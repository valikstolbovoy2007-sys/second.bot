# ТЗ: Упрощённый редактор шаблона карточки магазина

> Цель: убрать из редактирования шаблона карточки HTML-теги, синтаксис
> условий `{?var:...}` и необходимость помнить названия переменных.
> Супер-админ должен собирать карточку как конструктор из готовых блоков,
> не зная синтаксиса.

---

## 1. Что сейчас (контекст)

- Шаблон лежит в `bot_config[shop_card_template]` как одна строка.
- Поддерживается мини-DSL: `{var}`, `{?var:body}`, `{?!var:body}`.
- Редактируется через раздел «🎨 Шаблон карточки» в супер-админке:
  пользователь присылает целиком новый шаблон сообщением.
- Файлы:
  - `services/card_template.py` — DSL, рендер, дефолтный шаблон,
    список переменных, `validate`.
  - `services/card_render.py` — высокоуровневый рендер
    (`format_shop_card`, `render_with_template`).
  - `handlers/superadmin/template.py` — UI редактирования.

**Что остаётся как есть:** контекст переменных (`build_context`),
сама модель «один глобальный шаблон для всех магазинов», аудит и кэш.

---

## 2. Что меняется

Шаблон карточки превращается в **упорядоченный список блоков**. Каждый
блок — это семантически законченный кусок карточки (заголовок, цена,
завоз, адрес и т.п.). Супер-админ работает с этим списком — не со строкой.

### 2.1 Список блоков (фиксированный набор)

Идентификаторы стабильны (используются в БД). Названия — для UI.

| id              | Название в UI            | Что показывает (используемые переменные)                |
|-----------------|--------------------------|---------------------------------------------------------|
| `header`        | 🏪 Заголовок             | `name`, `chain`                                         |
| `separator_top` | ━━━ Разделитель сверху   | `sep`                                                   |
| `price_today`   | 💰 Цена сегодня          | `price_today_line` (уже с эмодзи и `<b>`)               |
| `day_label`     | 📅 Метка дня цикла       | `day_label`                                             |
| `arrival_block` | 🚚 Блок завоза           | `next_arrival_date`, `days_to_arrival`, `price_start`   |
| `max_discount`  | 💸 Макс. скидка          | `max_discount_date`, `days_to_max_discount`             |
| `cycle_len`     | 🗓 Длина цикла           | `cycle`                                                 |
| `today_event`   | ⚡ Событие сегодня       | `today_event`                                           |
| `separator_mid` | ━━━ Разделитель внутри   | `sep`                                                   |
| `address`       | 📍 Адрес                 | `address`                                               |
| `description`   | 📝 Описание              | `description`                                           |
| `tracked_badge` | ⭐ Метка отслеживания    | `is_tracked`                                            |

> Набор блоков **фиксирован в коде**. Новые блоки добавляет только
> разработчик (нужны новые переменные / новая логика контекста).

### 2.2 Что может СА с блоком

Для каждого блока:
- **Включить / выключить** (toggle). Выключенный блок не рендерится.
- **Переместить вверх / вниз** (изменить порядок). Порядок сохраняется.
- **Редактировать обрамляющий текст**: префикс и суффикс блока + опционально
  тело (см. ниже). HTML вручную не пишется — форматирование берётся из
  Telegram (длинное нажатие → жирный/курсив/ссылка/цитата), `html_text`
  превращает его в HTML.
- **Сбросить блок к стандартному** (один блок, не весь шаблон).

> **Авто-скрытия пустых блоков нет.** Если переменные блока пусты для
> конкретного магазина — блок всё равно рендерится в том виде, как его
> собрал СА (может оказаться пустая или полупустая строка). Видимость
> блока полностью контролирует СА через toggle. Если внутри тела блока
> есть встроенные `{?var:...}` — они продолжают работать (это часть
> default-шаблона блока, написанного разработчиком), но это не блочный
> уровень.

### 2.3 Что НЕ может СА

- Создать новый блок или удалить существующий из списка (только
  выключить).
- Менять, какие переменные используются в блоке (это закодировано
  разработчиком в шаблоне блока).
- Писать произвольный HTML руками.

### 2.4 «Сырой» HTML-режим

Сохраняем кнопку «🛠 Расширенный режим (HTML)» в супер-админке. Она
открывает старый интерфейс с полным шаблоном-строкой (то, что сейчас
лежит в `handlers/superadmin/template.py` — целиком). Если СА сохранил
шаблон в сыром режиме — блочный редактор показывает баннер «Сейчас
активен ручной шаблон, при сохранении блоков он будет перезаписан»
с кнопками «Перейти к ручному режиму» и «Сбросить ручной и пользоваться
блочным».

Источник истины при рендере: если в `bot_config` есть валидный
`shop_card_template` (ручной) — используется он. Иначе собирается
из `shop_card_blocks`. Иначе — зашитый `DEFAULT_TEMPLATE`.

## 3. Модель данных и рендер

### 3.1 Хранение

Новая запись в `bot_config`:
- Ключ: `shop_card_blocks`
- Значение: JSON-строка, массив объектов:

```json
[
  {"id": "header",        "enabled": true,  "text": "🏪 <b>{name}</b>{?chain: · <i>{chain}</i>}"},
  {"id": "separator_top", "enabled": true,  "text": "{sep}"},
  {"id": "price_today",   "enabled": true,  "text": "{price_today_line}"},
  ...
]
```

Поле `text` — это исходник блока в том же мини-DSL, что сейчас. Но СА
его **в UI не видит как DSL**: он редактирует только «текст до» / «текст
после» (см. 3.3), а в JSON это сохраняется уже с подстановками.

Старый ключ `shop_card_template` остаётся как fallback на одну миграцию
и для «сырого режима» (см. 2.4).

### 3.2 Реестр блоков (в коде)

В `services/card_blocks.py` (новый файл):

```python
@dataclass(frozen=True)
class BlockSpec:
    id: str
    title: str          # Название в UI («🚚 Блок завоза»)
    default_text: str   # DSL-шаблон по умолчанию
    editable: bool      # можно ли редактировать text (для разделителей — нет)
    fields: tuple[BlockField, ...]  # пользовательские поля (префикс/суффикс/метки)
```

Авто-скрытия по пустой переменной нет. Видимость блока — только через
`enabled` в JSON конфигурации (см. 3.1).

### 3.3 Что СА реально редактирует в блоке

Чтобы не показывать СА `{?…:…}`, на каждый блок есть **простая форма**:

- **Префикс** (строка) — что напечатать перед основной переменной.
  Пример для `price_today`: `«Сегодня: »`.
- **Суффикс** (строка) — что напечатать после.
- **Включён?** (bool).
- **Порядок** (число).

Для блоков без редактируемого тела (`separator_top`, `tracked_badge`) —
только toggle и порядок.

Для блоков со сложным телом (`arrival_block`) — даём редактирование
**меток**, а не самого тела:
- Метка завоза («🚚 Следующий завоз: »)
- Метка цены завоза («В день завоза: »)
- ...

Все эти «префиксы/суффиксы/метки» — поля конкретного `BlockSpec`. У
каждого блока — свой набор полей, которые СА видит. Пример полей
`arrival_block`:

```
[ Заголовок строки ] «🚚 Следующий завоз:»
[ Подпись цены     ] «В день завоза:»
[ ]  Показывать цену завоза, если она задана
[✓]  Включить блок
[↑] [↓]  Переставить
```

Под капотом эти поля собираются в DSL-строку блока по заранее
заданному шаблону. **СА DSL не видит.**

### 3.4 Сборка финального шаблона

`services/card_render.py`:

1. Если в bot_config есть `shop_card_template` (ручной режим) и он
   валиден — используем его (старый путь). Иначе:
2. Загружаем `shop_card_blocks` из bot_config (или DEFAULT_BLOCKS).
3. Для каждого включённого блока в порядке:
   - Берём `text` из JSON (или собираем из полей формы блока).
   - Подставляем переменные через существующий `render(...)`.
4. Склеиваем через `\n`.
5. Схлопываем тройные переносы (как сейчас).

Старый `render(template, ctx)` остаётся — он используется внутри сборки
блоков и для «сырого режима».

## 4. UI супер-админки

Раздел «🎨 Шаблон карточки» меняет вид:

```
🎨 Шаблон карточки магазина
Сейчас: блочный конструктор · 12 блоков, 9 включены

[👁 Предпросмотр]

🔘  🏪 Заголовок              [✓] [✏️] [↑↓]
🔘  ━━━ Разделитель           [✓]      [↑↓]
🔘  💰 Цена сегодня           [✓] [✏️] [↑↓]
🔘  📅 Метка дня цикла        [ ] [✏️] [↑↓]
🔘  🚚 Блок завоза            [✓] [✏️] [↑↓]
... и т.д. ...

[↩️ Сбросить всё к стандартному]
[🛠 Расширенный режим (HTML)]
[← В супер-админку]
```

- `[✓]` — toggle on/off (callback).
- `[✏️]` — открыть редактор одного блока.
- `[↑↓]` — перемещение (два отдельных callback-а).
- В шапке — сводка (сколько блоков, сколько включено).

### 4.1 Редактор одного блока

```
✏️ Блок: 🚚 Блок завоза
Так выглядит блок в карточке сейчас (тестовый магазин):

🚚 Следующий завоз: Чт, 14 май (через 5 дней)
В день завоза: 1 200 ₽/кг

[Заголовок строки]  → «🚚 Следующий завоз:»  [✏️]
[Подпись цены]      → «В день завоза:»       [✏️]
[✓] Показывать цену завоза, если она задана
[✓] Блок включён

[👁 Предпросмотр всей карточки]
[↩️ Сбросить этот блок к стандартному]
[← Назад]
```

При нажатии на `[✏️]` рядом с полем — FSM-состояние «жду новое значение»,
СА присылает текст. Принимаем `message.html_text` (берёт Telegram-
форматирование) — но запрещаем символы `{` `}` в ответе (чтобы СА не
поломал DSL-структуру блока). При нарушении — понятная ошибка, FSM
остаётся.

### 4.2 Предпросмотр

Кнопка «👁 Предпросмотр» рендерит **всю карточку** через сборку из
текущей конфигурации блоков и `_sample_shop()` — ровно так, как её
увидит пользователь. HTML-исходник в `<pre>` не показываем.

---

## 5. Миграция

1. Если `shop_card_blocks` в bot_config отсутствует — рендер использует
   зашитый в коде дефолтный массив блоков (`DEFAULT_BLOCKS` в
   `card_blocks.py`). Этот дефолтный массив даёт **визуально идентичный**
   результат текущему `DEFAULT_TEMPLATE`. Проверяем golden-тестом.
2. Если присутствует только старый `shop_card_template` (ручной шаблон):
   - При первом заходе в редактор показываем баннер «У вас задан
     ручной шаблон. Перейти к блочному (он сбросит ручной) или продолжить
     ручным?».
   - Никакой автоконвертации строки → блоков не делаем (слишком хрупко).

---

## 6. Валидация

- Длина итогового собранного шаблона ≤ 4000 (как сейчас).
- В пользовательских строках (префиксы/суффиксы/метки) запрещены
  символы `{` и `}` — выдаём понятную ошибку.
- После каждого сохранения — пробный рендер на `_sample_shop()`. Если
  падает — откатываем изменение, ошибку показываем СА, FSM остаётся.
- В `bot_config` пишем только провалидированный JSON.

## 8. Аудит

Добавляем actions:
- `template.block.toggle` (resource = block id)
- `template.block.move` (resource = block id, payload = new index)
- `template.block.edit` (resource = block id, payload = field name)
- `template.block.reset` (resource = block id)
- `template.blocks.reset_all`

Старые `template.update` / `template.reset` остаются — для сырого режима.

---

## 9. Что в этой итерации НЕ делаем

- Разные шаблоны под разные сети / магазины.
- Шаблоны под уведомления (notifier пользуется тем же шаблоном через
  `format_shop_card` — отдельная задача).
- Превью на реальном магазине из БД (только `_sample_shop`).
- Drag-n-drop порядка — только `↑/↓` (Telegram не даёт DnD).
- Условия по конкретным значениям (например, «показать если cycle = 14»).
  Только «есть / нет переменной».

---

## 10. Решения по открытым вопросам

1. Сырой HTML-режим **оставляем** (см. 2.4).
2. Перемещение блоков — **две отдельные кнопки** `↑` и `↓` рядом с
   блоком.
3. Названия блоков из 2.1 — **утверждены**.
4. **Без авто-скрытия** пустых блоков. Видимость — только через toggle
   супер-админа.
5. В предпросмотре HTML-исходник **не показываем** — только готовая
   карточка как у пользователя.
